# 비전 → 아두이노 시리얼 연동 보고서

- 작성일: 2026-11-17
- 상태: **초안 (커밋 전, 팀 검토 필요)**
- 대상 저장소: `uav-tracker-test` (비전), `uav-vision-tracker` (펌웨어/문서)

---

## 1. 요약

비전(PC)에서 탐지한 드론의 위치를 아두이노(제어부)로 보내는 경로를 구현했습니다.

```
카메라 → YOLO + ByteTrack → 목표 1개 선택 → 화면 중앙 기준 각도 오차 계산
      → USB 시리얼 "<valid,ax,ay>\n" (매 프레임) → 아두이노 수신/파싱 → 팬·틸트 모터
```

- PC는 드론 **중심 좌표 대신 화면 중앙 기준 "각도 오차"** 를 보냅니다. 단위는 0.1° 정수입니다.
- 메시지는 사람이 읽을 수 있는 **텍스트 한 줄**입니다. 예: `<1,250,-17>` = 오른쪽 25.0°, 위 1.7°.
- 아두이노 쪽은 **수신부가 완성된 뼈대 코드**를 제공합니다. 제어 담당은 함수 3개(`onTarget`, `onLost`, `onLinkTimeout`)만 채우면 됩니다.

## 2. 설계 결정과 이유

| # | 결정 | 이유 | 검토했던 대안 |
|---|---|---|---|
| 1 | **USB 시리얼 (115200 baud)** | 아두이노 Uno R3에 USB-시리얼 변환칩이 내장되어 있어 케이블 하나로 됨. 추가 부품이 필요 없음 | 블루투스/무선: MVP에는 불필요 |
| 2 | **ASCII 텍스트 `<valid,ax,ay>\n`** | 시리얼 모니터로 바로 읽고 손으로 입력해 테스트 가능. 30fps × 약 15바이트 = 450 B/s로 대역폭의 약 4%만 사용 | int16 바이너리: 전송 시간이 약 0.6ms 줄지만 카메라·추론 지연(수십~100ms)에 비하면 1% 미만이고, 체크섬·엔디안 처리로 디버깅이 어려워짐 |
| 3 | **`<` `>` 시작/끝 마커** | 포트를 연 직후 잘린 데이터나 조각난 수신을 걸러냄. 메시지 경계를 확실히 구분 | 줄바꿈만 사용: 중간부터 읽으면 잘못된 숫자가 들어올 수 있음 |
| 4 | **중심 픽셀 대신 "중앙 기준 오차"** | 제어의 목적은 오차를 0으로 만드는 것. 아두이노가 해상도를 몰라도 됨 | `cx, cy` 원본 + 해상도 전송: 아두이노에서 계산이 필요 |
| 5 | **각도 단위 (0.1° 정수)** | 해상도나 카메라가 바뀌어도 펌웨어와 게인 튜닝을 다시 할 필요가 없음. 서보 각도와 단위가 같아 직관적. 정수라서 AVR에서 `sscanf`로 간단히 파싱 | 픽셀 오차: 해상도마다 게인이 달라짐 / ±1000 정규화: 카메라를 바꾸면 다시 튜닝해야 함 / 실수 전송: Uno의 `sscanf`는 `%f` 미지원 |
| 6 | **`atan` 기반 각도 변환 (대각선 화각 95.8°)** | 카메라 STCOM biz FHD60F의 스펙은 대각 95.8°, 가로 88.4°, 세로 57.6°. 광각이라 비례식 근사는 화면 중간에서 약 5° 틀림. 대각선 화각에서 픽셀 초점거리를 구해 가로·세로를 같은 식으로 계산 | 선형 비례: 오차가 큼 |
| 7 | **매 프레임 전송, 드론이 안 보여도 `<0,0,0>` 전송** | 메시지 자체가 하트비트 역할. 아두이노는 "드론 놓침"과 "PC 연결 끊김"을 구분할 수 있음 | 탐지됐을 때만 전송: 끊김과 놓침을 구분할 수 없음 |
| 8 | **목표 1개만 전송 (추적 ID 우선, 없으면 신뢰도 최대)** | 팬·틸트는 한 번에 하나만 따라갈 수 있음. ID를 유지하면 여러 대 사이에서 왔다갔다하는 걸 막음 | 전체 목록 전송: 아두이노가 선택해야 하고 메시지 길이가 가변 |
| 9 | **송신이 밀리면 버림 (`write_timeout=0.05`)** | 오래된 좌표보다 다음 프레임의 최신 좌표가 나음. 비전 루프가 멈추지 않게 함 | 블로킹 전송: 아두이노가 멈추면 PC도 멈춤 |

## 4. 인터페이스 명세 (PC → 아두이노)

### 4.1 링크

| 항목 | 값 |
|---|---|
| 물리 연결 | USB 케이블 (Uno R3 내장 USB-시리얼) |
| 설정 | 115200 baud, 8N1 |
| 방향 | PC → 아두이노 단방향 (아두이노의 `Serial.print`는 디버그 용도로만 사용) |
| 전송 주기 | 카메라 프레임마다 (약 15~30 Hz, 추론 속도에 따라 달라짐) |
| 연결 직후 | Uno R3는 포트가 열리면 리셋되므로 PC가 2초 기다린 뒤 전송 시작 |

### 4.2 메시지 형식

```
<valid,ax,ay>\n
```

| 필드 | 타입 | 범위 | 의미 |
|---|---|---|---|
| `valid` | 정수 | `0` 또는 `1` | 1 = 드론 탐지됨, 0 = 못 찾음 |
| `ax` | 정수 (0.1°) | 실사용 약 −440 ~ +440 | 가로 각도 오차. **+면 드론이 화면 오른쪽** |
| `ay` | 정수 (0.1°) | 실사용 약 −285 ~ +285 | 세로 각도 오차. **+면 드론이 화면 아래쪽** |

- 문자 인코딩: ASCII. 공백 없음. 끝에 `\n`이 붙지만 아두이노는 `>`를 기준으로 메시지 끝을 판단합니다.
- `valid=0`일 때 `ax`, `ay`는 항상 `0`이며 의미가 없습니다.
- 실사용 범위는 STCOM biz FHD60F(대각선 화각 95.8°), 16:9 해상도 기준입니다(가로 ±44.0°, 세로 ±28.5°). 1280×720과 1920×1080 모두 화면이 잘리지 않아 같은 값을 씁니다.
- 펌웨어 유효성 검사: `valid ∈ {0,1}`, `|ax|, |ay| ≤ 900` (±90°). 벗어나거나 형식이 틀리면 **그 메시지만 버립니다.**

**예시**

| 메시지 | 의미 |
|---|---|
| `<1,0,0>` | 드론이 정확히 화면 중앙에 있음 |
| `<1,250,-17>` | 드론이 오른쪽 25.0°, 위 1.7°에 있음 |
| `<1,-440,285>` | 드론이 왼쪽 끝, 아래쪽 끝에 있음 |
| `<0,0,0>` | 드론 안 보임 (PC는 정상 연결 상태) |

### 4.3 상태와 동작

| 상황 | 판단 기준 | 호출되는 함수 | 기본 동작 (예시 코드) |
|---|---|---|---|
| 드론 보임 | 새 메시지, `valid=1` | `onTarget(ax, ay)` (메시지당 1번) | 오차의 K 비율만큼 서보 이동 |
| 드론 놓침 | 새 메시지, `valid=0` | `onLost()` (메시지당 1번) | 제자리 유지 |
| 연결 끊김 | 300ms 동안 올바른 메시지 없음 | `onLinkTimeout()` (끊긴 순간 1번) | 제자리 유지 |
| PC 프로그램 정상 종료 | 마지막에 `<0,0,0>` 전송 후 포트 닫음 | `onLost()` → 300ms 후 `onLinkTimeout()` | 제자리 유지 |

### 4.4 좌표·각도 계산 (PC 측, 참고용)

```
cx, cy           = 바운딩 박스 중심 (원점: 화면 왼쪽 위, x→오른쪽, y→아래)
error_x, error_y = cx − W/2,  cy − H/2                      (픽셀)
f                = (√(W²+H²) / 2) / tan(DFOV / 2)            (픽셀 단위 초점거리)
ax, ay           = round(atan(error / f) × 10)  [도 → 0.1°]
```

## 5. 제어부(아두이노) 담당자 가이드

### 5.1 해야 할 일

1. `pan_tilt_tracker` **폴더째** 받아서 아두이노 IDE로 엽니다. 폴더 이름과 `.ino` 파일 이름이 같아야 합니다.
2. 기존 코드를 합칩니다.
   - 기존 `setup()`과 `loop()` 내용을 뼈대의 **[기존 코드 넣는 곳]** 으로 옮깁니다. `setup()`과 `loop()`는 하나씩만 있어야 합니다.
   - 모터 구동 코드는 `onTarget()` 안으로 옮깁니다. 서보 예시는 지워도 됩니다.
   - `loop()`에서 `readSerial()`과 `handleMessage()`는 **매번** 호출되어야 합니다.
3. 보드를 **Arduino Uno**로 선택하고 업로드합니다.

### 5.2 꼭 지켜야 할 것

| 규칙 | 이유 |
|---|---|
| `Serial.begin(115200)` 유지 | PC와 속도가 다르면 글자가 깨짐 |
| `delay()` 사용 금지 (`millis()` 사용) | delay 동안 수신을 처리하지 못해 지연이 쌓임. 64바이트 버퍼는 메시지 약 4개분 |
| `Serial.readString()`, `parseInt()` 사용 금지 | 기본 타임아웃 때문에 최대 1초씩 멈춤 |
| 제어량은 **새 메시지가 왔을 때만** 갱신 | loop는 초당 수천 번, 메시지는 초당 약 30번. 같은 오차를 반복 적용하면 끝까지 돌아감. 뼈대가 이미 처리하므로 `onTarget` 안에서만 움직이면 됨 |
| DC/스텝모터는 `onLinkTimeout()`에서 **반드시 정지** | PC가 죽어도 모터가 계속 돌지 않게 하기 위함. 서보는 명령이 없으면 제자리를 유지하므로 비워둬도 됨 |
| 모터 전원은 외부 전원 사용, **GND 공통 연결** | 아두이노 5V 핀으로는 서보 전류가 부족해 보드가 리셋되고 통신이 끊김 |
| PC 프로그램을 실행할 때는 시리얼 모니터 닫기 | COM 포트는 한 프로그램만 열 수 있음 |

### 5.3 조정할 값 (`[제어부]` 상단)

| 상수 | 기본값 | 조정 방법 |
|---|---|---|
| `PAN_DIR`, `TILT_DIR` | `1` | 드론 반대 방향으로 돌면 `-1`로. 기구를 장착한 방향에 따라 다름 |
| `K` | `0.4` | 한 번에 오차의 몇 %만큼 움직일지. 떨리면 0.2~0.3으로 낮추고, 느리면 높임. 1.0 이상이면 지연 때문에 진동함 |
| `DEADBAND` | `15` (1.5°) | 중앙 근처에서 미세하게 떨리면 키움 |
| `PAN_MIN/MAX`, `TILT_MIN/MAX` | 0–180, 30–150 | **기구가 부딪히지 않는 실제 범위로 반드시 측정해서 설정** |
| `PAN_PIN`, `TILT_PIN` | 9, 10 | 실제 배선에 맞춤 |
| `TIMEOUT_MS` | 300 | 보통 그대로 둠 (프레임 간격의 약 10배) |

### 5.4 제어 관련 참고

- `ax`, `ay`는 "목표가 지금 카메라 정면에서 몇 도 떨어져 있는지"입니다. 카메라가 팬·틸트 위에 달려 있으므로 **필요한 회전량과 같은 단위**입니다. 이론적으로는 그만큼 돌리면 중앙에 오지만, 영상과 추론 지연(약 50~150ms) 때문에 실제로는 일부(K)만 움직이는 방식이 안정적입니다.
- 예시는 P 제어입니다. 성능이 부족하면 PI/PD 제어나 속도 제한을 시도해 볼 수 있습니다. 이때 시간 간격은 고정값이 아니라 메시지 간격(`millis()` 차이)으로 계산하세요.
- 서보 `write()`는 1° 단위입니다. 더 부드럽게 움직이려면 `writeMicroseconds()`를 고려하세요.
- 세로 방향은 **+가 아래**입니다. 틸트 서보의 각도가 커질 때 카메라가 위를 보는지 아래를 보는지 확인한 뒤 `TILT_DIR`을 정하세요.

### 5.5 PC 없이 단독 테스트

1. 업로드한 뒤 시리얼 모니터를 엽니다(115200 baud).
2. 아래 메시지를 차례로 입력합니다.

| 입력 | 기대 결과 (예시 코드, K=0.4) |
|---|---|
| `<1,200,0>` | 팬이 +8° 이동 (0.4 × 20°) |
| `<1,-200,0>` | 팬이 −8° 이동 (원위치) |
| `<1,0,200>` | 틸트가 +8° 이동 |
| `<1,10,10>` | 움직이지 않음 (데드밴드 1.5° 이내) |
| `<0,0,0>` | 움직이지 않음 (`onLost` 호출) |
| `abc`, `<1,2>` | 무시됨 |

### 5.6 실제 모터: MKS SERVO42D

팀 모터는 **MKS SERVO42D**입니다. 이름에 SERVO가 들어가지만 RC 서보가 아니라, **NEMA17 스텝모터에 엔코더와 FOC 폐루프 드라이버를 붙인 제품**입니다. 탈조가 없어서 자주, 조금씩 움직이는 추적에 적합합니다. 명령 방법은 펄스(STEP/DIR), 시리얼(RS485/UART, MODBUS-RTU), CAN 세 가지이고, 팀 코드에는 두 방식이 이미 올라와 있습니다.

| 팀 코드 | 방식 | `onTarget()`에서 할 일 |
|---|---|---|
| `firmware/2motor_test_2` | 펄스 (STEP/DIR, 1/16 마이크로스텝) | 각도를 스텝으로 변환(1스텝 = 0.1125°, 10° ≈ 89스텝)한 뒤 펄스 출력. **"회전 중 추가 입력 무시"는 추적에서 쓰면 안 되므로**, 새 메시지가 오면 목표를 갱신하도록 바꿔야 함 |
| `firmware/motor_control/` | CAN (MCP2515, 500 kbps) | 오차 각도만큼 "상대 위치 이동" 명령을 보냄. 가감속은 드라이버가 처리. 명령 형식은 Makerbase 공식 매뉴얼로 확인 |

- **핀 충돌:** CAN 모듈은 10(CS)~13번 핀을 씁니다. 뼈대 코드의 서보 예시(`TILT_PIN = 10`)와 겹치므로, CAN 방식을 쓸 때는 서보 예시를 지워야 합니다.
- **정지 처리:** CAN **속도 모드**(`motor_set_speed`)로 돌린다면 `onLinkTimeout()`에서 정지 명령을 꼭 보내야 합니다. 보내지 않으면 PC가 꺼져도 모터가 계속 돕니다.
- **범위 제한:** 스텝모터는 절대 각도를 기억하지 않으므로, `PAN_MIN/MAX` 같은 범위 제한을 누적 각도로 직접 계산해서 지켜야 합니다.
- 모터와 팬·틸트 사이에 기어나 벨트가 있다면 각도에 감속비를 곱해야 합니다.
- 통신 쪽(USB 시리얼)은 CAN(SPI)과 겹치지 않으므로 그대로 사용하면 됩니다. `motor_control`도 이미 `Serial.begin(115200)`을 쓰고 있습니다.
- 조이스틱 수동 조종(`software/communication/servo_controller.zip`, 메시지 `P,pan,tilt`)은 별도 모드입니다. 두 메시지는 첫 글자(`<`와 `P`)로 구분되므로 나중에 한 스케치로 합칠 수 있습니다. 다만 COM 포트는 한 프로그램만 열 수 있어서 두 프로그램을 동시에 실행할 수는 없습니다.

## 8. 실행 방법

```powershell
# 비전 (uav-tracker-test 폴더)
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
.\.venv\Scripts\python.exe main.py --serial auto            # 아두이노 자동 탐색
.\.venv\Scripts\python.exe main.py --serial COM5            # 직접 지정 (장치 관리자 → 포트에서 확인)
.\.venv\Scripts\python.exe main.py --serial COM5 --dfov 95.8 --classes 0   # 쿼드콥터만
```

콘솔에 출력되는 JSON의 `serial` 필드에서 마지막으로 보낸 메시지를 확인할 수 있습니다.
